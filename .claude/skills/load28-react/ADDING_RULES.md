# 규칙 추가 프로세스 v4.1

> 새 규칙/레퍼런스를 load28-react 스킬에 추가할 때 따르는 프로세스.
> 규칙은 하나의 위치가 아닌 **여러 레이어에 동시 배치(적층)**될 수 있다.

---

## 핵심 원리: 다층 검증 (Multi-Layer Verification)

규칙 배치는 "어디 하나에 넣을까"가 아니라, **각 레이어를 독립적으로 판단**한다:

| 레이어 | 시점 | 역할 | 예 |
|--------|------|------|-----|
| 슬롯 임베딩 | 설계 | 물리적 위반 봉쇄 | C-04(7칸), S-16(cleanup 필수 칸) |
| Grammar A | 코드 변환 전 | 슬롯값 의미 검증 (스키마 횡단) | A-01(의존성 방향), S-07(Context 분리) |
| Design Guard | 슬롯 완료 후 | 설계 결정 확인 (스키마 전용) | P-02(가상화), P-08(dynamic import) |
| Grammar B | 코드 변환 후 | 코드 구문 스캔 | N-01(PascalCase), S-01(직접 변경 금지) |
| 레퍼런스 | 슬롯 채우기 참고 | 모범 구현 패턴 | 태그 기반 코드 |
| 규칙 문서 | 항상 (교육) | 규칙의 WHY | 모든 규칙의 원본 |

**위반 심각도가 높을수록 더 많은 레이어에 배치한다.**

---

## Step 1: 중복/충돌 검증 (Gate)

1. **_grammar.md 전체** 스캔 (Section A + B)
2. **6개 규칙 문서 전체**에서 의도 유사 규칙 검색 (키워드 + 의도 기반, 교차 카테고리 포함)
3. 판정:
   - 완전 중복 → **추가 중단**
   - 부분 중복 → 기존 규칙 확장/수정으로 대체 검토
   - 충돌 → 기존 규칙과의 우선순위/예외 관계 명시
   - 신규 확인 → Step 2로

---

## Step 2: 규칙 코드 부여

- 카테고리 결정:

| 카테고리 | 문서 |
|---------|------|
| A (아키텍처) | architecture.md |
| N (네이밍) | naming-conventions.md |
| S (상태·데이터) | state-and-data.md |
| P (성능) | performance.md |
| C (컴포넌트) | component-patterns.md |
| T (타입·테스트·접근성) | testing-a11y.md |

- 번호: 해당 카테고리 마지막 번호 + 1
- **코드 불변 원칙**: 삭제/폐기해도 번호 재사용 금지

---

## Step 3: 규칙 문서 작성 (항상 필수)

대상 파일: 카테고리별 문서에 추가.

포맷:
```markdown
## {코드}: {규칙명}

**분류:** ALWAYS / NEVER / {조건부}

**WHY:** {이 규칙이 존재하는 이유}

​```tsx
// ❌ BAD: {위반 코드 예시}
// ✅ GOOD: {준수 코드 예시}
​```

**검증:** {위반 판단 기준}
```

---

## Step 4: 영향 스키마 식별 + 배치 위치 결정

### 4-0. 영향 스키마 매트릭스

9개 스키마 각각에 대해 "이 규칙이 해당 스키마의 코드 생성에 영향을 주는가?" 판단:

| 스키마 | 영향 여부 |
|--------|----------|
| component | YES / NO |
| hook | YES / NO |
| context | YES / NO |
| store | YES / NO |
| api-layer | YES / NO |
| test | YES / NO |
| type | YES / NO |
| barrel | YES / NO |
| module | YES / NO |

**Fast-track**: 특정 스키마에만 해당하는 것이 명백한 경우, 해당 스키마만 표시하고 이유 명시.
(예: "barrel 전용 — export 구문은 barrel 파일에만 존재")
→ Step 6-1의 grep 교차 검증이 누락 안전장치로 작동.

### 4-1. 슬롯 임베딩 (영향 스키마 각각에 대해 독립 판단)

슬롯의 물리적 구조로 위반을 원천 봉쇄 가능한가?
- YES → `schemas/{스키마}.md` 슬롯 구조 수정
- NO → 다음으로

### 4-2. Grammar A / Design Guard (영향 스키마 각각에 대해 독립 판단)

코드 생성 전 슬롯 값만으로 검증 가능한가?
- YES + **여러 스키마 공통** → `schemas/_grammar.md` **Section A**에 등록
- YES + **특정 스키마 전용** → `schemas/{스키마}.md` **Design Guard**에 DG 항목 추가
- NO → 다음으로

**Grammar A vs B 판별 기준:**

| | Grammar A | Grammar B |
|---|---|---|
| 시점 | 코드 변환 전 | 코드 변환 후 |
| 대상 | 슬롯 값 (추상적) | 코드 텍스트 (구체적) |
| 성격 | 아키텍처 의미 검증 | 코딩 구문 규약 |
| 기준 | 슬롯 간 관계/방향 분석 | 정규식/패턴 매칭으로 검출 |

**Grammar A vs Design Guard 판별 기준:**

| | Grammar A | Design Guard |
|---|---|---|
| 적용 범위 | 여러 스키마에 공통 | 특정 스키마 유형에만 |
| 위치 | _grammar.md (중앙 집중) | 각 스키마 파일 (분산) |
| 판단 방식 | 위반/통과 이분법 | 해당/해당없음 + 조치 방법 |

### 4-3. Grammar B (독립 판단)

생성된 코드에서 패턴 스캔으로 검출 가능한가?
- YES → `schemas/_grammar.md` **Section B** 해당 카테고리에 등록
- NO → 다음으로

### 4-4. 다층 검증 판단

```
축 1: 위반 심각도
  높음 = 런타임 버그 (메모리 누수, 무한 루프, 성능 붕괴, 데이터 불일치)
  낮음 = 코드 스타일/컨벤션

축 2: 슬롯 봉쇄 완전성
  완전 = 물리적으로 위반 불가 (칸 수, 선택지, 고정값 + 코드 우회 불가)
  불완전/불가 = 우회 가능하거나 슬롯 임베딩 자체가 해당 없음

판단:
  심각도 높음 → 4-1~4-3 중 적용 가능한 모든 레이어에 배치 (최소 2개)
  심각도 낮음 + 완전 봉쇄 → 단일 위치 가능
  심각도 낮음 + 봉쇄 불완전 → 가장 적합한 1개 + Grammar B 추가 고려
```

**"슬롯만 충분" 조건 (극소수)**: 물리적 완전 봉쇄 + 코드 우회 불가 + 심각도 낮음
(예: C-04 props 7칸, S-08 도구 선택)

### 가드레일: 4-1~4-3 모두 NO?

→ 정말 자동 강제가 불가능한 프로세스 원칙인지 재확인
→ YES → 규칙 문서만 (Step 3으로 충분)
→ NO (실은 슬롯/스캔 가능) → 4-1~4-3 재판단

## Step 5: 레퍼런스 코드 (조건부)

1. **필요성 판단**: 구체적 코드 패턴을 요구하는가? → 추가 / 단순 금지 규칙? → 불필요
2. **기존 레퍼런스 확인**: frontmatter의 `rules:` 필드에 추가만으로 충분? → 기존 파일 수정
3. **태그 확인**: `_tags.md`에서 매칭 태그 검색 → 없으면 새 태그 등록
4. **새 레퍼런스 작성**:
   - 파일명: `{태그1}--{태그2}.md`, frontmatter에 `tags`/`rules` 필수
   - **SKILL.md Phase 1-A 프로토콜 준수**: 스키마 슬롯 채우기 → 코드 변환 → Grammar Scan
   - **도메인 비종속 플레이스홀더** 사용 (Entity, Resource, Item 등)
5. **피드백 검증**: 레퍼런스가 새 규칙의 슬롯을 자연스럽게 채울 수 있는가?
   - 불가능 → Step 4 슬롯 설계 재검토 (피드백 루프)

## Step 6: 최종 교차 검증 + 체크리스트

### 6-1. grep 교차 검증

```bash
grep "{규칙코드}" schemas/*.md
```

결과가 Step 4-0의 영향 스키마 매트릭스와 일치하는지 확인.
불일치 → 누락된 스키마 수정.

### 6-2. 완료 체크리스트

```
□ Step 1: 중복/충돌 없음 (전체 카테고리 교차 검증 완료)
□ Step 3: 규칙 문서 작성 완료 → {파일명}
□ Step 4-0: 영향 스키마 = [{목록}]
□ Step 4-1: 슬롯 임베딩 = {해당 스키마: ___ / 비해당}
□ Step 4-2: Grammar A = {해당/비해당} / DG = {해당 스키마: ___ / 비해당}
□ Step 4-3: Grammar B = {해당/비해당, 카테고리: ___}
□ Step 4-4: 다층 검증 = {해당: 추가 위치 ___ / 비해당}
□ Step 5: 레퍼런스 = {추가/기존수정/불필요} → {파일명}
□ Step 6-1: grep 교차 검증 통과
```

## 규칙 수정/폐기 (별도 프로세스 — 최소 원칙)

- **수정**: 규칙 코드 유지 + Step 4-0(영향 매트릭스)으로 모든 참조 위치 역추적 + 갱신
- **폐기**: 규칙 코드 재사용 금지 + `[DEPRECATED: {사유}]` 표시 + 모든 참조 위치에서 제거
- **번호 재할당 금지**: S-04를 폐기해도 다음 규칙은 S-18 (S-04 아님)
